Because a `px` workspace is just files, a git repo can be the source of truth for your
Prometheux ontologies — validated on every pull request and applied on every merge. `px`
runs headless in CI: authenticate with environment variables, no interactive login.

## Authenticate in CI

Skip `px login` and set two environment variables (they override any stored config):

```bash
export JARVISPY_URL="https://api.prometheux.ai/jarvispy/<org>/<user>"
export PMTX_TOKEN="<JWT>"
```

Store them as repository secrets. Any datasource secrets your files reference as
`${ENV_VAR}` must also be present in the environment at `apply` time.

## Validate on pull requests

`validate` is fully offline — no token, no platform — so it's a fast, cheap PR gate:

```yaml
# .github/workflows/prometheux-validate.yml
name: Validate Prometheux workspace
on:
  pull_request:
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pipx install prometheux
      - run: px validate --strict
```

`--strict` turns warnings into failures so a PR can't merge with, for example, a
concept-less ontology.

## Test logic on pull requests

[`px test`](/integrations/cli/command-reference#px-test-target) runs Vadalog programs on the
engine and checks the rows they produce, so a PR that changes a rule's results fails before
it merges. Keep the programs, their `*.test.yaml` cases and the expected CSVs in the repo,
and publish the JUnit report so the CI system shows each case:

```yaml
# .github/workflows/prometheux-test.yml
name: Test Vadalog programs
on:
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pipx install prometheux
      - run: px test tests/ --junit-xml reports/px-test.xml
        env:
          JARVISPY_URL: ${{ secrets.JARVISPY_URL }}
          PMTX_TOKEN: ${{ secrets.PMTX_TOKEN }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: px-test-report
          path: reports/px-test.xml
```

<Note>
Unlike `validate`, `px test` needs the platform and a running compute machine. Either keep
a machine running for CI, or start one in the job with `px compute start` and stop it in a
final step that runs `if: always()`. A machine takes a short while to accept work after it
starts.
</Note>

For a large suite, add `--replicas 2` (or `--replicas auto`) to the `px test` step: it
starts [engine workers](/integrations/cli/command-reference#running-a-suite-in-parallel)
beside the machine for the length of the run and removes them at the end, even when the
job is cancelled. Give the step a few extra minutes the first time, while the workers
start. Each worker is billed at the machine's hourly rate while it runs.

## Apply on merge to main

```yaml
# .github/workflows/prometheux-apply.yml
name: Apply Prometheux workspace
on:
  push:
    branches: [main]
jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pipx install prometheux
      - name: Plan (log the diff)
        run: px plan
        env:
          JARVISPY_URL: ${{ secrets.JARVISPY_URL }}
          PMTX_TOKEN: ${{ secrets.PMTX_TOKEN }}
      - name: Apply
        run: px apply -y
        env:
          JARVISPY_URL: ${{ secrets.JARVISPY_URL }}
          PMTX_TOKEN: ${{ secrets.PMTX_TOKEN }}
          PG_PASSWORD: ${{ secrets.PG_PASSWORD }}   # any ${ENV_VAR} your datasources use
```

<Note>
Run `px plan` before `px apply` in the job so the diff (including the downstream re-run
cascade) is captured in the build log for review/audit.
</Note>

## Sync the context layer

Apply the [context layer](/integrations/cli/context-as-code) the same way. Commit
`.px/context-state.json` so the sync stays idempotent across runs:

```yaml
# .github/workflows/prometheux-context.yml
name: Sync context to Prometheux
on:
  push:
    branches: [main]
    paths: ["context/**", "**/*.context.md"]
jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pipx install prometheux
      - run: px context apply --prune -y
        env:
          JARVISPY_URL: ${{ secrets.JARVISPY_URL }}
          PMTX_TOKEN: ${{ secrets.PMTX_TOKEN }}
```

## Exit codes for gating

CI can gate on exit codes directly (see the [command reference](/integrations/cli/command-reference#exit-codes)):

- `px validate` → `0` PASS, non-zero FAIL.
- `px test` → `0` every check passed, `1` a check failed, `2` the tests could not start.
- `px apply` → `0` on success; **non-zero if any concept was skipped** (with a summary) or
  on a hard error — so a partial apply fails the job.
- `px plan`, `px status` → `0`.

## Idempotency & state to commit

- **Project id** in `ontologies/<slug>/prometheux.yaml` — commit it so re-apply targets the
  same ontology (never creates a duplicate). If it's lost, `apply` reconciles by ontology name.
- **Context state** `.px/context-state.json` — commit it so `context apply` updates rather
  than re-creates notes.

A clean checkout that's already in sync plans as **no changes** — so re-running the apply
job is safe.

## Corporate runners

`px` honours `HTTPS_PROXY`, `NO_PROXY`, `PIP_INDEX_URL`, and
`REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE`, so it works on locked-down self-hosted runners
behind a proxy with a corporate CA. Install the signed wheel from your internal mirror
instead of the public one-liner. See [Installation → Corporate install](/integrations/cli/installation#corporate-and-enterprise-install).
