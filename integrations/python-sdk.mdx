The `prometheux_chain` Python SDK provides a high-level interface for working with all Prometheux platform features programmatically.

## Installation

```bash
pip install --upgrade prometheux-chain
```

## Configuration

```python
import prometheux_chain as px
import os

# Set your authentication token
os.environ['PMTX_TOKEN'] = 'YOUR_PMTX_TOKEN'

# Configure the backend URL
px.config.set('JARVISPY_URL', "https://api.prometheux.ai/jarvispy/{organization}/{username}")
```

## First API Call

```python
# Create a new ontology
ontology_id = px.save_ontology(ontology_name="my_first_ontology")
print(f"Created ontology: {ontology_id}")
```

## Unit-test a Vadalog program

`check_program` evaluates a program on the engine and compares each output predicate with
the rows you expect, given as a CSV file or as a list of rows. It never raises for a failed
check or an engine error: read `report.ok` and `report.summary()`, or call
`report.assert_ok()`, which raises `AssertionError` with the summary. That makes it fit
directly in a pytest suite:

```python
import prometheux_chain as px

def test_transitive_closure():
    program = open("programs/tc.vada").read()
    px.check_program(program, expect={"tc": "expected/tc.csv"}).assert_ok()

def test_reachability_includes_known_pairs():
    program = open("programs/tc.vada").read()
    report = px.check_program(program, expect={"tc": [[1, 4], [2, 4]]}, mode="contains")
    assert report.ok, report.summary()
```

- **Modes.** `exact` (the default) passes when the predicate produces the same rows, the
  same number of times. `contains` passes when every expected row is produced, whatever
  else is.
- **Values.** They are compared by meaning rather than spelling: `2`, `"2"` and `2.0` are
  equal, and so are `True`, `"true"` and Vadalog's `#T`. Expected CSVs have no header unless you pass
  `header=True`.
- **Inputs.** `params` and `compute` are passed to the evaluation as in `evaluate_program`.

`check_question` does the same for a program the natural-language translator writes from
a question. The generated program is kept on the report, so a failure shows what was run:

```python
report = px.check_question(
    "Edges 1->2, 2->3 and 3->4. Compute every pair (X,Y) where Y is reachable from X. Output as tc.",
    expect="expected/tc.csv",
)
print(report.program)
report.assert_ok()
```

When `expect` is a single CSV or list of rows, it is checked against `expect_predicate`,
or the generated program's last `@output` when that is not given. Each call counts as one
program generation in your usage.

<Note>
Both functions evaluate on your compute, so a machine must be running. The
[`px test`](/integrations/cli/command-reference#px-test-target) command runs the same checks
from files, and writes a JUnit report for CI.
</Note>

## Response Format

All REST API responses follow a consistent format:

```json
{
  "data": {},           // Response data (varies by endpoint)
  "message": "string",  // Human-readable message
  "status": "success"   // Status: "success" or "error"
}
```

The Python SDK automatically handles responses and returns the relevant data directly.

## Streaming responses

Some endpoints stream their output incrementally — the [AI Agent](/integrations/api-endpoints/agent)
chat, [Context Layer auto-seed](/integrations/api-endpoints/context-layer#auto-seed-from-data-sources),
and the concept run-stream. In the SDK these are exposed as **generator
functions**: iterate over them to consume events as they arrive instead of
waiting for the whole response.

```python
import prometheux_chain as px

# Agent chat — each event is a dict with a "type" and "data"
for event in px.agent_chat(ontology_id="ont_123", message="Find all transitive suppliers and run it"):
    if event["type"] == "content":
        print(event["data"]["chunk"], end="")
    elif event["type"] == "done":
        print("\n[done]")
```

Each yielded event mirrors the NDJSON frames documented on the corresponding API
Reference page. Streams terminate with a `done` event, or an `error` event if
something goes wrong mid-stream.

## API Categories

<Tip>
For a flat index of **every** `px.<function>` mapped to its endpoint, see the
[SDK Function Reference](/integrations/sdk-reference).
</Tip>

The API is organized into the following categories:

| Category | Description |
|----------|-------------|
| [**Config**](/integrations/config) | SDK configuration, LLM setup, and account/usage helpers |
| [**Authentication**](/integrations/api-endpoints/authentication) | Issue, list, and revoke API tokens |
| [**Ontologies**](/integrations/api-endpoints/ontologies) | Ontology management, templates, snapshots, create-from-context |
| [**Ontology Sharing**](/integrations/api-endpoints/sharing) | Share ontologies and manage inbox/outbox |
| [**Concepts**](/integrations/api-endpoints/concepts) | Concept execution, reordering, and management |
| [**Data Sources**](/integrations/api-endpoints/data) | Data connections, schema inference, file store, joins |
| [**Schema**](/integrations/api-endpoints/schema) | Schema persistence, node/edge roles, OWL import |
| [**Knowledge Graph**](/integrations/api-endpoints/knowledge-graph) | Graph building and analytics over concept output |
| [**Vadalog**](/integrations/api-endpoints/vadalog) | Vadalog program analysis and evaluation |
| [**Vadalingo**](/integrations/api-endpoints/vadalingo) | NL, SQL, RDF, and OWL to Vadalog translation |
| [**Apps**](/integrations/api-endpoints/apps) | App CRUD and versioning |
| [**Schedules**](/integrations/api-endpoints/schedules) | Automated concept runs on cron or data-change triggers |
| [**Context Layer**](/integrations/api-endpoints/context-layer) | Agent knowledge base: notes, search, ingestion |
| [**AI Agent**](/integrations/api-endpoints/agent) | Streaming conversational AI agent |
| [**Chat History**](/integrations/api-endpoints/chat-history) | Browse and manage agent chat sessions |
| [**Alerts**](/integrations/api-endpoints/alerts) | Monitoring webhooks and alert reprocessing |
| [**Compute**](/integrations/api-endpoints/compute) | Compute availability checks |

## Error Handling

The SDK raises exceptions for errors:

```python
import prometheux_chain as px

try:
    result = px.run_concept(ontology_id="invalid_id", concept_name="test")
except Exception as e:
    print(f"Error: {e}")
```
