---
title: "Ontology Sharing"
description: "Share ontologies with other users as viewer or editor, manage your outbox, and accept, leave, or sync shares from your inbox."
---

The Ontology Sharing API lets an ontology owner grant another user **viewer** or
**editor** access to an ontology, and lets the recipient accept, leave, and
reconcile shares from their inbox. Sharing issues a scoped token to the
recipient under the hood; the raw token is never returned to the sharer — it is
delivered to the recipient and claimed on accept.

All paths are relative to the [base URL](/integrations/rest-api#base-url) and
require [authentication](/integrations/api-endpoints/authentication). All
responses use the standard [envelope](/integrations/rest-api#response-envelope).

<Note>
Endpoints split into **sharer-side** (you own the ontology and grant access) and
**recipient-side** (an ontology has been shared with you). Recipient-side
endpoints additionally rely on your Supabase session, sent via the
`X-Supabase-Token` header, so row-level security scopes the results to you.
</Note>

## Sharer-side

### Share an ontology

Grant another user access to one of your ontologies. Identify the recipient by
`sub`, by `email`, or by `username` together with `organization`.

```
POST /ontologies/share
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `project_id` | body | yes | — | ID of the ontology to share. |
| `recipient` | body | yes | — | Recipient object: `{ "sub": "..." }`, `{ "email": "..." }`, or `{ "username": "...", "organization": "..." }`. |
| `share_role` | body | yes | — | `"viewer"` or `"editor"`. |
| `expires_in_minutes` | body | no | `null` | Lifetime of the share; omit or `null` for no expiration. |

```bash
curl -X POST "$BASE_URL/ontologies/share" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "'$PROJECT_ID'",
    "recipient": { "email": "alice@example.com" },
    "share_role": "viewer"
  }'
```

```jsonc
{
  "status": "success",
  "message": "Ontology shared successfully.",
  "data": {
    "share_id": "shr_a1b2...",
    "project_id": "proj_123",
    "share_role": "viewer",
    "status": "pending"
  }
}
```

### List shares (outbox)

Return every share you have created, most recent first. Optionally filter to a
single ontology.

```
GET /ontologies/share/list
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `project_id` | query | no | — | Filter the outbox to a single ontology. |

```bash
curl "$BASE_URL/ontologies/share/list" \
  -H "Authorization: Bearer $TOKEN"
```

`data` is an array of share objects (`share_id`, `project_id`, `share_role`,
`status`, recipient identity, and timestamps).

### Update the role on a share

Change a share between `viewer` and `editor` in place — the recipient is not
forced to re-accept. Updating to the role it already has is a no-op that returns
`data.changed = false`.

```
POST /ontologies/share/update-role
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `share_id` | body | yes | — | The share to update. |
| `share_role` | body | yes | — | New role: `"viewer"` or `"editor"`. |

```bash
curl -X POST "$BASE_URL/ontologies/share/update-role" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "share_id": "shr_a1b2...", "share_role": "editor" }'
```

```jsonc
{
  "status": "success",
  "message": "Share role updated successfully.",
  "data": { "share_id": "shr_a1b2...", "share_role": "editor", "changed": true }
}
```

### Revoke a share

Revoke access you previously granted. Pass either a `share_id`, or a
`project_id` together with a `recipient_sub`. Revoking is idempotent.

```
POST /ontologies/share/revoke
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `share_id` | body | conditional | — | The share to revoke. |
| `project_id` | body | conditional | — | Ontology ID — use with `recipient_sub` instead of `share_id`. |
| `recipient_sub` | body | conditional | — | Recipient's auth ID — use with `project_id`. |

```bash
curl -X POST "$BASE_URL/ontologies/share/revoke" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "share_id": "shr_a1b2..." }'
```

```jsonc
{
  "status": "success",
  "message": "Share revoked successfully.",
  "data": { "share_id": "shr_a1b2...", "status": "revoked" }
}
```

## Recipient-side

### List inbox

Return every share currently visible to you as a recipient — pending
invitations and already-accepted shares. Each entry is annotated with
`has_local_token` so you can tell "accepted on this workspace" from "accepted
elsewhere".

```
GET /ontologies/share/inbox
```

This endpoint takes no parameters.

```bash
curl "$BASE_URL/ontologies/share/inbox" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Supabase-Token: $SUPABASE_TOKEN"
```

`data` is an array of inbox entries (`share_id`, `project_id`, `share_role`,
`status`, `has_local_token`, sharer identity, and timestamps).

### Accept a share

Claim a pending share. The scoped token is vaulted into your workspace so you
can open the shared ontology. Idempotent for shares already accepted on this
workspace.

```
POST /ontologies/share/accept
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `share_id` | body | yes | — | The share to accept. |

```bash
curl -X POST "$BASE_URL/ontologies/share/accept" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Supabase-Token: $SUPABASE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "share_id": "shr_a1b2..." }'
```

```jsonc
{
  "status": "success",
  "message": "Share accepted successfully.",
  "data": { "share_id": "shr_a1b2...", "status": "accepted" }
}
```

### Leave a share

Detach yourself from a share you previously accepted (or a pending one). This
removes the local token and marks the share `left`. Idempotent.

```
POST /ontologies/share/leave
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `share_id` | body | yes | — | The share to leave. |

```bash
curl -X POST "$BASE_URL/ontologies/share/leave" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Supabase-Token: $SUPABASE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "share_id": "shr_a1b2..." }'
```

```jsonc
{
  "status": "success",
  "message": "Share left successfully.",
  "data": { "share_id": "shr_a1b2...", "status": "left" }
}
```

### Sync inbox

Reconcile your locally-vaulted shares against the source of truth. Local entries
whose share is no longer `accepted` (revoked, superseded, left, or missing) are
pruned. Use this as a safety net to catch up after a missed real-time update.

```
POST /ontologies/share/sync
```

This endpoint takes no parameters.

```bash
curl -X POST "$BASE_URL/ontologies/share/sync" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Supabase-Token: $SUPABASE_TOKEN"
```

```jsonc
{
  "status": "success",
  "message": "Inbox synced successfully.",
  "data": { "pruned": 1, "active": 3 }
}
```

## Warehouse tables

Sharing an ontology shares the concepts. These endpoints share the **stored
tables** underneath — a directory or table in your own warehouse area — with
another user, by granting them access on the storage itself.

Reach for this when someone needs to read your materialized output directly
from their own tools, rather than through your ontology. For sharing individual
uploaded files instead, see
[file sharing](/integrations/api-endpoints/data#file-sharing).

### Share a table

```
POST /warehouse/share
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `path` | body | yes | — | Path relative to your own warehouse area (e.g. `revenue_by_region`). |
| `grantee` | body | yes | — | `{ "username": …, "organization": … }`. |
| `permissions` | body | no | `r-x` | `r-x` for read, `rwx` for read and write. |

```bash
curl -X POST "$BASE_URL/warehouse/share" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "path": "revenue_by_region",
    "grantee": { "username": "analyst", "organization": "acme" },
    "permissions": "r-x"
  }'
```

### Unshare a table

Takes `path` and `grantee` and removes that grantee's access.

```
POST /warehouse/unshare
```

### Inspect access

Returns the access list currently in force on a path.

```
GET /warehouse/acl
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `path` | query | no | `""` | Path relative to your warehouse area. Empty means its root. |

```bash
curl -G "$BASE_URL/warehouse/acl" \
  --data-urlencode "path=revenue_by_region" \
  -H "Authorization: Bearer $TOKEN"
```

<Note>
All three resolve `path` under **your own** area, so you cannot share, revoke,
or inspect data you do not own — the authenticated caller is always the owner.
</Note>
