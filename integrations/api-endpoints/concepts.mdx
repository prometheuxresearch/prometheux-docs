---
title: "Concepts"
description: "Define, run, and read results from concepts — the units of logic and context at the core of a Prometheux project."
---

A **concept** is a unit of logic in a project that produces an output
predicate. Four kinds are executable programs — Vadalog, SQL, Cypher, and
Python — and two are configured rather than written: `context` concepts, which
expose unstructured notes as a queryable window, and `llm` concepts, which call
a language model from a prompt template. The Concepts API lets you create
concepts, run them (individually or as a dependency chain), read their results,
and track execution progress.

All paths are relative to the [base URL](/integrations/rest-api#base-url) and
require [authentication](/integrations/api-endpoints/authentication). All
responses use the standard [envelope](/integrations/rest-api#response-envelope).

## Save a concept

Create or update a concept. Saving a concept with an `existing_name` updates it
in place; otherwise a new concept is created.

```
POST /concepts/{ontology_id}/save
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `definition` | body | conditional | — | The concept body: Vadalog rules, a SQL or Cypher query, Python logic, or an LLM prompt template (per `concept_type`). Omit it for `context` concepts, which have no executable body. |
| `concept_type` | body | no | `"logic"` | One of `logic` (Vadalog), `sql`, `cypher`, `python`, `context`, or `llm`. See [Context and LLM concepts](/platform/context-and-llm-concepts). |
| `concept_name` | body | conditional | — | Required for every type except `logic`, which takes its name from the output predicate. |
| `concept_config` | body | conditional | — | Configuration for `context` and `llm` concepts, ignored for the other types. Required for `context`. See [Context and LLM concepts](/platform/context-and-llm-concepts). |
| `output_predicate` | body | no | `""` | The predicate this concept outputs. |
| `description` | body | no | — | Human-readable description. |
| `binds` | body | no | — | Bind annotations linking input/output predicates to data sources. |
| `force_overwrite` | body | no | `false` | Overwrite a conflicting concept instead of returning `409`. |

### Example

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/save" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "definition": "@output(\"location\").\nlocation(L) <- company(_, L).",
    "concept_type": "logic"
  }'
```

```jsonc
{
  "status": "success",
  "message": "Concept saved",
  "data": { "id": "cpt_8f2a..." }
}
```

## List concepts

Return all concepts in a project, enriched with their parsed code and binds.

```
GET /concepts/{ontology_id}/list
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |

```bash
curl "$BASE_URL/concepts/$PROJECT_ID/list" \
  -H "Authorization: Bearer $TOKEN"
```

`data` is an array of concept objects (name, type, definition, binds,
output predicate, description, group, and position).

## Get one concept

Return the same enriched object as `/list`, for a single concept. Use it when
you already know the name and do not want to pull the whole project.

```
GET /concepts/{ontology_id}/concept
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_name` | query | yes | — | Predicate name of the concept. |

```bash
curl -G "$BASE_URL/concepts/$PROJECT_ID/concept" \
  --data-urlencode "concept_name=transitive_suppliers" \
  -H "Authorization: Bearer $TOKEN"
```

A name that does not exist in the project returns `404`.

## Run a concept

Execute a concept and its dependency chain. The engine runs at most one job at
a time per workspace; see [Execution status](#execution-status) to track
progress.

```
POST /concepts/{ontology_id}/run/{concept_name}
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_name` | path | yes | — | The target concept to run. |
| `params` | body | no | `{}` | Runtime parameter values referenced by the program. |
| `run_mode` | body | no | `"auto"` | How much of the dependency chain to rebuild: `single`, `auto`, or `all`. See below. |
| `persist_outputs` | body | no | `true` | Persist output predicates so they can be read with [`/fetch`](#fetch-concept-results). |
| `compute` | body | no | — | [Compute](/integrations/rest-api#compute) target. |

**`run_mode` values**

- `single` — reuse every populated dependency as-is; rebuild only what is strictly
  missing to answer for the target concept. Cheapest.
- `auto` (default) — reuse dependencies that are provably fresh, rebuild the stale
  or unverifiable ones, and honour any frozen checkpoints.
- `all` — rebuild everything reachable in the dependency chain and override
  checkpoints. Most expensive; use as an escape hatch.

<Note>
`run_mode` replaces the older `force_rerun` boolean. For older clients, `force_rerun: true`
maps to `all` and `force_rerun: false` maps to `single`; new integrations should send
`run_mode`.
</Note>

### Example

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/run/location" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "persist_outputs": true }'
```

On success, `data` contains the execution result. On a run error, `status` is
`"error"` and `data` carries an `errorCode` and `errorMessage`:

```jsonc
{
  "status": "error",
  "message": "Evaluation failed",
  "data": { "errorCode": "VL0023", "errorMessage": "..." }
}
```

<Tip>
For long-running jobs, prefer firing the run and then polling
[Execution status](#execution-status) rather than blocking on the response. A
WebSocket variant, `/concepts/{ontology_id}/run-stream/{concept_name}`, streams
per-concept progress frames if you need live updates.
</Tip>

## Freeze a concept

Freeze a concept so no run rebuilds it, or unfreeze it again. A frozen concept
keeps whatever output it last produced: nothing re-derives it while it is
reached as a dependency of something else, so the concepts below it are not
rebuilt either. Running it directly still builds it — freezing says "do not
rebuild this on the way to something else", not "never build this".

Use it for a concept whose inputs are gone or unreliable, one expensive enough
that its consumers should reuse the last result, or one holding a result that
must not move while work continues around it.

```
POST /concepts/{ontology_id}/refresh-mode
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_name` | body | yes | — | The concept to freeze or unfreeze. |
| `refresh_mode` | body | yes | — | `"checkpoint"` to freeze, `"default"` to unfreeze. |

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/refresh-mode" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "concept_name": "supplier_snapshot", "refresh_mode": "checkpoint" }'
```

This endpoint sets only the freeze flag — the definition, the populated flag and
everything else are left alone. A freeze is honoured by `run_mode: "auto"` and
overridden by `run_mode: "all"`.

<Note>
A freeze holds against the world moving underneath a concept, not against the
concept itself changing. Editing the definition, or running with different
`params`, breaks it: the stored table would otherwise be served in place of one
it is not a substitute for.
</Note>

## Check freshness

Ask whether each concept's stored output still reflects its sources — judged
against the sources **as they are right now**, not against what was last
recorded. It answers "would a run rebuild this?" without paying for the run.

```
GET /concepts/{ontology_id}/freshness/check
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_name` | query | no | all | Check only this concept and its own chain. |
| `params` | query | no | — | JSON object of run parameters to judge against (see below). |
| `run_mode` | query | no | — | The run mode you intend to use: `single`, `auto`, or `all`. |

```bash
curl -G "$BASE_URL/concepts/$PROJECT_ID/freshness/check" \
  --data-urlencode "concept_name=transitive_suppliers" \
  --data-urlencode 'params={"min_tier":2}' \
  -H "Authorization: Bearer $TOKEN"
```

`data` is a map keyed by concept name:

```jsonc
{
  "status": "success",
  "message": "Freshness checked successfully",
  "data": {
    "transitive_suppliers": {
      "state": "stale",
      "reason": "source_moved",
      "tier": "exact",
      "last_run_at": "2026-09-20T11:04:00+00:00",
      "fingerprint": "…"
    }
  }
}
```

| Field | Meaning |
|---|---|
| `state` | `fresh`, `stale`, or `unknown`. |
| `reason` | Why: `matches`, `never_run`, `interrupted`, `source_moved`, `logic_changed`, `params_changed`, `upstream_changed`, `output_moved`, `non_deterministic`, `weak_evidence`, or `not_observed`. |
| `tier` | How trustworthy the evidence is: `exact`, `heuristic`, or `unknown`. The weakest input governs the verdict. |

<Note>
`unknown` is an honest answer, not a failure: the output matches what was
recorded, but at least one source cannot be trusted to have noticed a change.

Supplying `params` changes the question. Without it, each concept is judged
under the arguments its *own last run* used — which describes the stored
artifact. With it, each is judged under *these* arguments — which is what a run
would decide. For a parametric concept only the second form is meaningful: rows
built at one threshold are not an answer about another.
</Note>

<Warning>
Unlike `/list`, this endpoint contacts your data sources — one batched metadata
call per project, or per chain when `concept_name` is given. It writes nothing,
so it is safe to call, but do not put it on a poll loop the way you would
`/list`.
</Warning>

The two companion endpoints, `POST /concepts/{ontology_id}/freshness/record` and
`POST /concepts/{ontology_id}/freshness/invalidate`, exist for one caller: a
recipient of a filesystem share, whose run computes on its own compute but
writes the owning project's tables. They bracket such a write so the owner's
record does not describe rows a recipient overwrote. Ordinary integrations never
call them — a normal run keeps its own record.

## Fetch concept results

Read the persisted rows of an output predicate. This is the single endpoint for
all reads: paging, ordering, free-text search, and per-column filtering are all
optional and combine in one request. It reads already-materialized results and
never recomputes — run the concept first.

```
POST /concepts/{ontology_id}/fetch
```

`output_predicate` is a query parameter; everything else goes in the JSON body.

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `output_predicate` | query | yes | — | The predicate to read. |
| `params` | body | no | `{}` | Object of exact-match `column: value` pairs. |
| `search_term` | body | no | — | Free-text term OR-matched across all columns. |
| `column_filters` | body | no | — | Array of column filters, AND-combined. See below. |
| `page` | body | no | `1` | [Page](/integrations/rest-api#pagination) number. |
| `page_size` | body | no | `30` | Rows per page, `1`–`1000`. |
| `order_by` | body | no | — | String, e.g. `"0:asc,2:desc"`. |
| `total_count` | body | no | — | A row count you already know, to skip the `COUNT(*)`. Ignored on any filtered read. |
| `compute` | body | no | — | [Compute](/integrations/rest-api#compute) target. |

**Column filters**

Each entry is `{ "position": <0-based column index>, "operator": <operator>,
"value": <string or array of strings> }`. `operator` defaults to `contains`:

| Operator | Matches |
|---|---|
| `contains`, `starts_with`, `ends_with` | Case-insensitive substring / prefix / suffix. |
| `equals`, `not_equals` | Exact equality. `in` and `not_in` are accepted as aliases. |
| `greater_than`, `less_than`, `greater_than_or_equal`, `less_than_or_equal` | Ordered comparison — numeric for numeric values, lexicographic otherwise. |
| `is_null`, `is_not_null` | Null checks. These take no `value`. |

Filters are AND-combined. To OR several values on one column, pass an **array**
as `value` (`"any of"`) rather than repeating the filter.

### Example

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/fetch?output_predicate=location" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "search_term": "CA",
    "column_filters": [{ "position": 0, "operator": "starts_with", "value": ["Mountain", "Redmond"] }],
    "page": 1,
    "page_size": 30,
    "order_by": "0:asc"
  }'
```

```jsonc
{
  "status": "success",
  "message": "Success",
  "data": {
    "rows": [ ["Mountain View, CA"], ["Redmond, WA"] ],
    "count": 2,
    "page": 1,
    "page_size": 30
  }
}
```

<Note>
`/fetch` used to be a `GET` with query-string parameters, alongside a separate
`POST /concepts/{ontology_id}/search` for filtered reads. Both were replaced by
this single `POST`. Move `page`, `page_size`, `order_by`, and `params` out of the
query string and into the JSON body; `output_predicate` stays in the query string.
</Note>

## Query a concept with SQL

Run a single read-only SQL `SELECT` over one populated concept — for aggregates,
`GROUP BY`, and joins against the concept's own rows that `/fetch` cannot express.
Reference the concept by name in `FROM`. A row cap is always enforced, and the
concept must already exist and be populated.

```
POST /concepts/{ontology_id}/query
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_name` | body | yes | — | The concept to query. |
| `sql` | body | yes | — | A single read-only `SELECT` or `WITH` statement. |
| `compute` | body | no | — | [Compute](/integrations/rest-api#compute) target. |

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/query" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "concept_name": "location",
    "sql": "SELECT state, COUNT(*) AS n FROM location GROUP BY state ORDER BY n DESC"
  }'
```

## Find similar concepts

Semantic search across every concept in every project you can access — used to
find reuse candidates before authoring something new.

```
GET /concepts/search-similar
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `query` | query | yes | — | Free-text description of the concept you are looking for. |
| `top_k` | query | no | server default | Maximum number of matches. |
| `exclude_project_id` | query | no | — | A project to leave out of the search. |

```bash
curl "$BASE_URL/concepts/search-similar?query=supplier%20risk%20score" \
  -H "Authorization: Bearer $TOKEN"
```

`data` is `{ "count": <n>, "matches": [ ... ] }`.

Set the display order of concepts in a project. Pass the concept names in the

```
POST /concepts/{ontology_id}/reorder
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |
| `concept_names` | body | yes | — | Array of concept names in the desired order. |
| `group` | body | no | — | Restrict reordering to concepts in this group. |

```bash
curl -X POST "$BASE_URL/concepts/$PROJECT_ID/reorder" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "concept_names": ["raw_data", "cleaned", "final_report"] }'
```

```jsonc
{
  "status": "success",
  "message": "Concepts reordered successfully",
  "data": null
}
```

## Execution status

When a concept runs, the platform persists a snapshot of the run (one per run,
most recent 50 kept per project). These read-only endpoints report the state of
the latest run — they do not start one.

### Single project

```
GET /concepts/{ontology_id}/execution-status
```

| Parameter | In | Required | Default | Description |
|---|---|---|---|---|
| `ontology_id` | path | yes | — | The ontology ID. |

```jsonc
{
  "status": "success",
  "message": "Execution status",
  "data": {
    "execution_id": "f1c2...",
    "project_id": "proj_123",
    "target_concept": "final_report",
    "order": ["raw_data", "cleaned", "final_report"],
    "total": 3,
    "statuses": {
      "raw_data": { "status": "success" },
      "cleaned":  { "status": "running" }
    },
    "status": "running",
    "failure_reason": null,
    "started_at": "2026-06-19T10:00:00+00:00",
    "updated_at": "2026-06-19T10:00:04+00:00",
    "finished_at": null,
    "duration_ms": null
  }
}
```

The top-level `data.status` is the primary field:

| Value | Meaning |
|---|---|
| `idle` | No run history (single-project endpoint only). |
| `running` | A run is in progress. The currently-executing concept is the key in `statuses` whose `status` is `running`. |
| `success` | The run completed successfully. |
| `error` | The run failed — see `failure_reason`. |
| `cancelled` | The run was cancelled. |
| `interrupted` | The connection dropped or the server restarted mid-run. |

`success`, `error`, `cancelled`, and `interrupted` are terminal. Poll roughly
every 1.5 s while `running`, and stop once the status is terminal or `idle`.

### All projects (batch)

Takes no parameters — it reports on every project in your workspace.

```
GET /concepts/execution-statuses
```

`data` is a map keyed by `project_id`, where each value is the same snapshot as
above. Only projects whose latest run is `running`, `error`, `cancelled`, or
`interrupted` appear — **a project absent from the map is idle** (never run, or
its last run succeeded).

## Other operations

| Operation | Endpoint | Notes |
|---|---|---|
| Generate a description with the LLM | `POST /concepts/{ontology_id}/generate-description` | Body: `concept_name`. Returns `{ "description": "..." }`. |
| Read (or lazily generate) a description | `GET /concepts/{ontology_id}/description` | Query: `concept_name`. |
| Ask a question over predicate data | `POST /concepts/{ontology_id}/llm` | Body: `predicate_names`/`predicate_data`, `question`. Returns `{ "response": "..." }`. |
| Export results to CSV / download a file | `GET /concepts/{ontology_id}/download` | Query: `path`, `export_csv`, `concept_name`. Returns the raw file, not the envelope. |
| Delete concepts | `POST /concepts/{ontology_id}/cleanup` | Body: `concept_names` (omit to delete all). |
| Check whether a share grants filesystem access | `GET /concepts/{ontology_id}/share-warehouse` | Returns `{ "filesystem_shared": bool }` for the calling recipient. Read by the [share](/integrations/api-endpoints/sharing) layer; `false` when you are not a live recipient of the project. |
