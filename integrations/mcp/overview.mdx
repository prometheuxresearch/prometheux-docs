Connect AI agents to Prometheux using the [Model Context Protocol (MCP)](https://modelcontextprotocol.io) — an open standard that enables AI assistants to interact with external tools and data sources.

Prometheux offers three MCP integration options:

- **[Local MCP Server](/integrations/mcp/local)** (`prometheux-mcp`): Runs on your machine — works with Claude Desktop, Claude Code, Cursor, and any stdio-capable client. **Recommended for coding agents.**
- **[Remote MCP Server](/integrations/mcp/remote)** (`px-remote-mcp-server`): Cloud-hosted option that works with any MCP-compatible client via OAuth authentication
- **Built-in MCP Server** (Snowflake Native App only): Automatically registered when the app starts — Cortex Agents and Snowflake Intelligence can discover Prometheux tools with no external setup. See the [Native App guide](/get-started/installation/snowflake#cortex-agent-integration-mcp) for details.

## What is MCP?

The Model Context Protocol allows AI agents to:
- **Discover** available tools and resources
- **Execute** operations through a standardized interface
- **Access** external data sources and APIs

With Prometheux's MCP integration, you can use natural language to interact with your ontologies, list concepts, and execute reasoning — all directly from your preferred AI agent.

## Available Tools

Both MCP servers dynamically expose the following tools to AI agents. The tool catalog is served by the Prometheux backend, so new capabilities are available automatically as they are added to the platform.

Required parameters are shown in **bold**; the rest are optional.

<Note>
Most clients fetch the tool catalog once, when the connection opens, and cache it
for the rest of the session. If a tool starts rejecting a parameter that this
page documents, your client is probably holding an older copy of the schema —
reconnect to the server to pick up the current one.
</Note>

### Ontologies

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_ontologies` | List every ontology you can access, including ones shared with you | — |
| `create_ontology` | Create a new empty ontology | **`name`**, `description` |
| `delete_ontology` | Permanently delete an ontology and everything in it | **`ontology_id`**, `confirm`, `scope` |
| `list_templates` | List the curated template ontologies in the Prometheux catalogue | — |
| `get_template` | Read one template's concepts as read-only reference material | **`template_id`** |

### Data sources

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_data_sources` | List all data sources with their predicate names, bind annotations, field schemas, and row counts | — |
| `preview_data_source` | Preview the first rows of a connected data source | **`bind_annotation`**, `limit` |
| `create_csv_datasource` | Materialise inline rows as a CSV data source that Vadalog can bind to | **`ontology_id`**, **`predicate_name`**, **`columns`**, **`rows`**, `description` |
| `connect_file_as_datasource` | Register a tabular file already on disk as a queryable data source | **`file_path`** |
| `delete_data_source` | Permanently disconnect a data source from the workspace | **`bind_annotation`**, `scope` |

### Concepts — read and run

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_concepts` | List all concepts in an ontology with their schema, population state, and folder | **`ontology_id`** |
| `get_concept` | Return full detail for one concept, including its current definition | **`ontology_id`**, **`concept_name`** |
| `search_similar_concepts` | Semantic search across all of your ontologies, to find reuse candidates | **`query`**, `exclude_ontology_id`, `top_k` |
| `run_concept` | Execute a concept and its dependency chain through the reasoning engine | **`ontology_id`**, **`concept_name`**, `params`, `force_rerun`, `persist_outputs` |
| `fetch_concept` | Page through the rows of an already-populated concept without recomputing | **`ontology_id`**, **`concept_name`**, `page`, `page_size`, `params`, `column_filters`, `order_by` |
| `query_concept` | Run one read-only SQL `SELECT` over a populated concept, for aggregates and `GROUP BY` | **`ontology_id`**, **`concept_name`**, **`sql`** |

### Concepts — authoring

| Tool | Description | Parameters |
|------|-------------|------------|
| `validate_concept` | Check a concept body before saving it, at no LLM cost | **`definition`**, `concept_type`, `concept_name`, `ontology_id`, `concept_config` |
| `create_concept` | Save a new concept of any of the six kinds | **`ontology_id`**, `definition`, `concept_type`, `concept_name`, `description`, `concept_config`, `group`, `confirm_new` |
| `update_concept` | Overwrite an existing concept's definition | **`ontology_id`**, **`concept_name`**, `definition`, `concept_type`, `description`, `concept_config`, `group` |
| `delete_concept` | Permanently delete a concept | **`ontology_id`**, **`concept_name`**, `scope` |

<Note>
**Writing a concept**

`concept_type` is one of `logic` (Vadalog), `sql`, `cypher`, `python`, `context`,
or `llm`, and defaults to `logic`. The body always goes in `definition` — a
Vadalog program, a query, a Python body, or an LLM prompt template, depending on
the type.

`context` concepts are the exception: they have no body at all, and are
configured entirely through `concept_config`. `llm` concepts use `definition`
for the prompt and `concept_config` for the output columns and model settings.
See [Context and LLM concepts](/platform/context-and-llm-concepts).

`create_concept` also guards against duplication: if a similar concept already
exists in another of your ontologies, the save is rejected with
`similar_existing_concepts`, and you re-issue the call with `confirm_new: true`
to proceed.
</Note>

### Snapshots

| Tool | Description | Parameters |
|------|-------------|------------|
| `create_ontology_snapshot` | Take a point-in-time snapshot of an ontology | **`ontology_id`**, `description` |
| `list_snapshots` | List an ontology's snapshots, newest first | **`ontology_id`**, `scope` |
| `restore_snapshot` | Restore an ontology to a snapshot, overwriting its current state | **`ontology_id`**, **`snapshot_id`**, `scope` |
| `delete_snapshot` | Permanently delete one snapshot | **`ontology_id`**, **`snapshot_id`**, `scope` |

`restore_snapshot` takes an automatic safety snapshot before it overwrites anything.

### Schema

| Tool | Description | Parameters |
|------|-------------|------------|
| `get_ontology_schema` | Load the schema graph, where nodes are entity types and edges are relationships | **`ontology_id`** |
| `save_ontology_schema` | Save or replace the complete schema graph | **`ontology_id`**, **`ontology_schema_data`** |

### Apps

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_apps` | List every app across all ontologies | — |
| `get_app` | Load a single app with its full definition | **`ontology_id`**, **`app_id`** |
| `get_app_schema` | Return the JSON Schema for an app definition | — |
| `save_app` | Create or update an app; omit the definition's top-level `id` to create | **`ontology_id`**, **`app`** |
| `publish_app` | Publish an app, so viewers get a frozen snapshot of the current draft | **`ontology_id`**, **`app_id`** |
| `unpublish_app` | Remove the published snapshot, returning the app to draft-only | **`ontology_id`**, **`app_id`** |
| `delete_app` | Permanently delete an app and its version history | **`ontology_id`**, **`app_id`** |

Call `get_app_schema` before `save_app` — it returns the authoritative JSON Schema
for the app definition, along with the authoring guide.

### Context Layer

| Tool | Description | Parameters |
|------|-------------|------------|
| `save_context_note` | Persist a durable note the agent should remember in later turns | **`scope`**, **`kind`**, **`title`**, **`text`**, `ontology_id`, `supersedes` |
| `list_context_notes` | Browse the Context Layer for the current user or ontology | **`scope`**, `ontology_id`, `kinds`, `activation` |
| `search_context_notes` | Semantic search over all saved notes, global and per-ontology | **`query`**, `limit` |
| `get_context_for_concept` | Return the notes attached to a concept, or every annotated concept | **`ontology_id`**, `concept_name` |
| `promote_context_to_concept` | Hand a note's text and predicates to the agent so it can author a concept | **`note_id`**, **`ontology_id`** |
| `delete_context_note` | Permanently delete a context note | **`note_id`** |
| `ingest_document_as_context` | Chunk and embed a long document, saving each chunk as a note | **`file_path`**, `scope`, `ontology_id` |
| `extract_concepts_from_document` | Run a concept-shaped extraction pass over an ingested document | **`document_id`**, `ontology_id` |
| `get_user_rules` | Return your standing rules, the same ones the in-app assistant loads | `ontology_id` |

Here `scope` is the note's own scope — `global` or `project` — rather than the
workspace scope used elsewhere. `kind` is `preference` or `fact`.

| `get_skill` | Fetch one skill's full playbook | **`skill_id`** |

### Compute machines

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_machines` | List the catalogue plus your enabled and disabled machines | — |
| `get_machine_status` | Real-time pod status for one of your machines | **`user_machine_id`** |
| `start_machine` | Add a catalogue machine to your compute list — provisions it, not billable | **`machine_id`**, `machine_name` |

### Scheduled runs

| Tool | Description | Parameters |
|------|-------------|------------|
| `list_policies` | List the scheduled or triggered runs configured for an ontology | **`ontology_id`**, `concept_name`, `scope` |
| `get_policy` | Return one policy with its trigger config and last-run status | **`ontology_id`**, **`policy_id`**, `scope` |
| `get_policy_runs` | Execution history for a policy, most recent first | **`ontology_id`**, **`policy_id`**, `limit`, `offset`, `scope` |
| `create_policy` | Re-run a concept on a cron schedule, or when its data changes | **`ontology_id`**, **`concept_name`**, **`trigger_type`**, **`trigger_config`**, `enabled`, `scope` |
| `update_policy` | Change a policy's schedule, or enable and disable it | **`ontology_id`**, **`policy_id`**, `trigger_config`, `enabled`, `scope` |
| `delete_policy` | Permanently delete a policy and unschedule its job | **`ontology_id`**, **`policy_id`**, `scope` |
| `trigger_policy` | Run a policy's concept immediately | **`ontology_id`**, **`policy_id`**, `scope` |

`trigger_type` is either `cron`, whose config looks like
`{"cron_expression": "0 6 * * *"}`, or `data_change`, whose config looks like
`{"check_interval_minutes": 30}`.

### Vadalog and company knowledge

| Tool | Description | Parameters |
|------|-------------|------------|
| `search_vadalog_docs` | Search the Vadalog documentation and return ready-to-use examples | **`query`** |
| `get_company_info` | Search the Prometheux company knowledge base | **`query`** |
| `request_clarification` | Pause and ask you a structured multiple-choice question rather than guess | **`question`**, **`options`**, `scope_picker`, `allow_custom`, `context` |

<Tip>
**Parameter defaults**

Tools that expose a `scope` parameter accept `"user"` or `"organization"` and
default to `"user"`; tools that omit it operate on your personal workspace. On
`run_concept`, both `force_rerun` and `persist_outputs` default to `true`.

On `update_concept`, omitting `description`, `concept_config`, or `group` leaves
that field unchanged — which is different from passing an empty value, since an
empty `concept_config` clears it and an empty `group` moves the concept back to
the root.
</Tip>

<Note>
**Long-running tools**

`run_concept`, `ingest_document_as_context`, and `extract_concepts_from_document`
advertise themselves as long-running through the `prometheux/long_running` hint
in `tools/list`, so clients can keep the connection alive and surface progress
instead of timing out.
</Note>

## Example Usage

Once configured, just chat naturally with your AI agent. The agent will automatically use the Prometheux MCP tools when relevant.

**Example queries:**
> "What ontologies do I have?"

> "What concepts are available in my customer-analytics ontology?"

> "Run the churn_prediction concept in the customer-analytics ontology"

> "Write a concept that finds all transitive suppliers for a company"

> "Summarise each supplier's risk notes into a table of company, risk level, and reason"

> "Create an app showing the results of churn_prediction"

> "What does the Vadalog documentation say about recursive rules?"

The AI agent will automatically:
- Call the appropriate Prometheux MCP tools
- Parse the results
- Present them in a readable format
- Answer follow-up questions about the data
